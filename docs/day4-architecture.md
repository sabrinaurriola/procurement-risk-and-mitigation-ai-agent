## 4. Architecture
```
 n8n Form ► n8n Set(request_id) ► POST /assessments ─────────────► FastAPI ► worker thread ► LangGraph run_assessment
 (intake)                         (X-API-Key, wait ≤150 s)           │  │                       (read-only DB, Tavily, GDELT, OpenAI)
                                                                     │  ├─ file store runs/assessments/  ◄── AUTHORITATIVE record + run marker
                                                                     │  └─ EventSink ► Supabase ops.operational_events (INSERT-only role; outbox file) [planned]
 200 finished | 504/409/transport ► bounded GET polling ◄───────────┘
 completed|partial ► Notion archive (full report) ► Gmail notification ► events
 failed            ► NO Notion row ► operator Gmail notice (error code only) ► events
```
| Component | Owns | Does not |
|---|---|---|
| Python/LangGraph | analysis, validation, assessment status, report | send or store externally |
| FastAPI | request validation, auth, idempotency, single-flight, deadline, authoritative record, event derivation/writes, Notion block rendering | business content, calling Notion/Gmail |
| n8n | intake, request_id, routing on `assessment_status`, bounded polling, Notion/Gmail calls, delivery retries, operator alert | analysis, LLM, DB access, **starting a second assessment** |
| Supabase `ops` | append-only operational log | reports, evidence, prompts |
| Notion | human-readable archive, human-review status, archive/delivery dedupe record | feeding anything back into the agent |
| Gmail | notification (status, counts, link) | carrying report text, recipients from input |

## 5. Statuses (never merged)
| Layer | Values | Owner |
|---|---|---|
| **`run_state`** (execution of a request) | `running` · `finished` | FastAPI. A request that is running has **no** assessment status |
| **`assessment_status`** (result of a finished run) | `completed` · `partial` · `failed` (the existing `status`, kept as an alias for n8n) | FastAPI record (authoritative) |
| **`archive_status`** (Notion; completed/partial only) | `pending` · `incomplete` · `stored` · `failed` (the Notion property; **events record outcomes only**: `incomplete`, `stored`, `failed`) | n8n → Notion property + event |
| **`delivery_status`** (Gmail; also the operator notice for failed runs) | `pending` · `draft_created` · `sent` · `failed` (the Notion property; events record `sent`, `failed`). **`draft_created` is not `sent`**: the mock workflow creates drafts only, so `sent` is never written by it | n8n → Notion property (where a row exists) + event |
| `human_review` (Notion only) | Pending review · Accepted · Needs changes · Rejected · Not applicable | a person; nothing reads it automatically |
A `failed` assessment is **never** archived in the normal Notion report database.

## 6. FastAPI execution model — IMPLEMENTED (S1)
* The assessment runs in a **server-owned worker thread**; the HTTP handler only waits (≤ `ASSESSMENT_DEADLINE_SECONDS`, default 150). A deadline hit returns **504 `ASSESSMENT_TIMEOUT` meaning "still running"**; the worker is never cancelled, the record is never marked failed because of a timeout, and nothing is re-run.
* While running: `GET /assessments/{id}` → `202 {"run_state":"running","assessment_status":null,"started_at":…,"overdue":bool}` + `Retry-After`. A repeated `POST` (same id, same hash) → `409 ASSESSMENT_IN_PROGRESS`; same id, other parameters → `409 REQUEST_ID_CONFLICT`; another id while one runs → `429 BUSY`.
* The finished record is written **atomically** (temp file + fsync + `os.replace`, bounded retry on the transient Windows sharing violation) **before** the worker is released, so a poller sees either `202` or the complete result. If the file write fails the record is served from memory until restart (logged); a restart then reports the request as interrupted, which is true.
* **Restart recovery:** a `{id}.run.json` marker with no live worker in this process means the previous process died mid-run. The request becomes a stored `failed` record with `ASSESSMENT_INTERRUPTED`, never re-run (paid); a new `request_id` is required. This is decided only when the worker is known to be dead, never on a timeout. Detection happens at the next access of that id.
* **Idempotency:** `request_id` + SHA-256 of `ingredient, horizon_months, assessment_date, mode`. Same id + hash after completion = replay of the stored envelope (`idempotent_replay:true`, zero tool/LLM calls, also after a restart); a stored `failed` is replayed too.
* **Safe errors:** every error is `{"request_id","run_state","assessment_status":null,"error":{"code","message"}}` with fixed messages. No paths, hosts, credentials or exception text (the worker drops exception messages and logs only the class).
* **Auth:** `X-API-Key` (constant-time compare); the app refuses to start without `ASSESSMENT_API_KEY`; `/health` is open and returns only `status, version, live_enabled, db`. Docs/OpenAPI endpoints are disabled.
* **Live mode:** the gate exists (403 without `ALLOW_PAID_CALLS=1`) but live is **not wired** in S1 (501 `LIVE_NOT_AVAILABLE` even with the flag). Wired and approved in S7.
* **Database:** the mock runner reads real data through the existing read-only session; the API layer writes nothing to the database.
* **S1 limitations (honest):** one process only (the single-flight registry is in memory; do not run several workers); no request-body size limit or rate limiting (local, keyed); the in-memory finished cache and the store are not pruned; a sync endpoint holds one worker-pool thread for up to the deadline; interrupted runs are detected lazily; `POST …/events` (the n8n event relay) is not built; `notion-blocks` and `notion-verify` were added on 12 Nov (section 18).

## 7. n8n behaviour (design; the workflow JSON is authored and SIMULATED only — see section 18)
* **Form Trigger acknowledgement — pending integration verification.** Assumption: the Form Trigger can respond immediately ("form submitted") while the execution continues and holds the synchronous `POST` (≤180 s). **Not proven.** Fallbacks: respond when the workflow finishes with a short confirmation page, or Webhook + Respond to Webhook. Verified only in S4.
* **Bounded polling after an uncertain POST (never re-POST).** POST outcomes → action: `200` → proceed; `504 ASSESSMENT_TIMEOUT`, `409 ASSESSMENT_IN_PROGRESS` or a transport timeout → enter the poll loop. Loop: Wait 10 s → `GET /assessments/{id}`; `202` → continue; `200` → proceed on `assessment_status`; GET `5xx`/transport error → counts as a failed poll (max 3 consecutive). **Limit: 24 polls (about 4 minutes) after the POST wait.** Exhausted while still `202` (or `overdue:true`) → operator e-mail "still running, request_id X"; the workflow ends; the operator redelivers later by submitting the same `request_id` (GET only). A `404` after a transport error means the POST may never have registered: **operator alert, no automatic re-POST**; resubmitting the same `request_id` is safe because the API deduplicates. Workflow execution timeout ≥ 15 minutes. `409 REQUEST_ID_CONFLICT`, `429 BUSY`, `401`, `422`, `403` are not polled: they alert/notify immediately.
* **Failures of archive/delivery never create a new assessment.** After the first successful POST every branch uses GET only. Redelivery = intake with an existing `request_id` → `IF request_id supplied` → `GET` (404 ⇒ stop with a message; never fall back to POST).

### 8.3 The draft migration `sql/drafts/002_ops_events.sql`
Effect if later approved: creates schema `ops`, table `ops.operational_events` (+ unique index on `event_key`, index on `(request_id, occurred_at)`), role `ops_writer` (LOGIN, no password, NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT; role settings `search_path = ops, pg_catalog`, `statement_timeout = 5s`, `idle_in_transaction_session_timeout = 10s`), RLS enabled with one INSERT policy for `ops_writer`, `GRANT USAGE ON SCHEMA ops` and `GRANT INSERT` on the one table, revocation from PUBLIC and from the Supabase API roles (`anon`, `authenticated`, `service_role`) when present, and the record `002` in `procurement.schema_migrations`. It touches no `procurement` table. Plain `CREATE` (no `IF NOT EXISTS`): an existing schema, table or role aborts the transaction.
Constraints (each mirrored in Python): enumerations for component, event type (11), severity, mode, assessment/archive/delivery status; patterns for `request_id`, `event_key` (also must start with `request_id|`) and `error_code`; non-negative metrics; `detail` must be a JSON object ≤ 4,096 bytes with only the 22 allowed keys; coupling rules — component `n8n` exactly for archive/delivery types, `assessment_status` exactly on `assessment.finished`, archive/delivery status must match the event type, duration only on finished/timeout, tokens and cost only on finished. **NULL trap:** a CHECK passes when it evaluates to NULL, so the coupling checks use `IS NOT DISTINCT FROM` and `COALESCE`; shared test rows (`..._NULL_TRAP`) cover them.
**Value-level privacy (new).** A key allow-list alone does not stop a permitted key from carrying free text, so every `detail` value is checked against a fixed form. *Python* (`DETAIL_VALIDATORS` in `src/api/events.py`, strict types; `bool` is not an integer): counters are integers 0…2³¹−1; `source` ∈ {tavily, gdelt, policy, filtering, other}; `status_class` ∈ {ok, partial, unavailable, not_configured, not_used, not_run, fallback, filtered, other}; `status` matches `^[A-Z][A-Z0-9_]{1,39}$` (a reason code, no spaces, so no sentence fits); `benchmark_status` ∈ {available, stale, unavailable}; `financial_status` ∈ {available, unavailable}; `notice_kind` ∈ {report, operator}; `notion_page_id` is a UUID; `report_sha256` is 64 lowercase hex; `kinds` keys come from the pruned report sections {risks, mitigation_options, supplier_candidates, recommended_actions, other} (a malformed removal entry becomes `other`, so a claim word can never become a key); `tool_calls` ≤ 10 lowercase names with integer values. `events_from_envelope` classifies instead of copying: research text becomes class + reason code, an error code that is not `[A-Z_]{1,64}` becomes `UNKNOWN_ERROR`, out-of-range numbers are dropped. *SQL* (`ck_detail_values`, `ck_detail_no_sensitive`): the text-valued keys above must be JSON strings in the same vocabularies/patterns (a JSON null or number fails), and `detail::text` must not match the same sensitive-marker list as Python (`SENSITIVE_MARKERS`: URL separator, `@`, bearer, api key, password, secret, token, authorization, `sk-…`, connection-string prefixes), including inside nested keys. **What each layer guarantees.** The nested JSON value rules (`kinds` keys/values, `tool_calls` keys/values, counter types and ranges, booleans) are enforced by **Python only**. PostgreSQL enforces a narrower set: the 22-key top-level allow-list, the 4,096-byte cap, the top-level text-valued rules above, and the sensitive-marker pattern. **The SQL does not independently guarantee that arbitrary nested text can never be inserted**: a holder of the `ops_writer` credential who bypasses the Python model could store short non-marker text inside `kinds`/`tool_calls` or as a numeric-looking value, within 4 KB. The privacy guarantee for nested content therefore depends on every writer going through the Python model (FastAPI is the single writer by design; the n8n relay is validated by the same model). A stricter SQL rule for nested values is possible later but is not claimed or implemented. Validation messages name the key, never the value, and the service logs only the exception class.
The Python side matches: `EVENT_TYPES`, `DETAIL_KEYS`, `INSERT_COLUMNS`, `to_row()`, the coupling validator, `DETAIL_MAX_BYTES = 4000` (stricter than the database's 4,096 so formatting differences can never trip the CHECK; with the value rules the limit is only a backstop). `tests/test_ops_events_sql.py` parses the SQL and fails if enumerations, columns (and order), detail keys, patterns or limits drift; it also asserts the privilege list is exactly `USAGE` on `ops` and `INSERT` on the table, no password, no `IF NOT EXISTS`, the runner cannot see the draft, and this section mentions every event type, detail key and column.

### 8.4 Gate G-OPS (security test plan)
Three stages; any failure keeps `NullEventSink`/outbox and the gate closed.
**R — rehearsal in a rolled-back transaction (needs approval: it runs DDL, though nothing is meant to persist).** Run by `python -m src.db.ops_rehearsal --execute` (dry run without the flag; connects to nothing). *Why a harness:* the draft is wrapped in `BEGIN … COMMIT`, so pasting it inside an outer transaction would **commit** it before any final `ROLLBACK`. The harness therefore:
1. **Strips only the two outer wrappers, lexically.** `src/db/sql_guard.py` tokenises comments, `'…'` (with `''`), `"…"` identifiers and `$tag$…$tag$`, splits on top-level `;`, requires the first statement to be exactly `BEGIN` and the last exactly `COMMIT`, and drops those two *statements* (no string replacement; every remaining statement is a verbatim slice of the file). Unsupported syntax is rejected, not guessed: `E'…'`, `U&'…'`, `B'…'`, `X'…'`, `N'…'`, `U&"…"`, backslashes outside literals, unterminated literals/comments, a final statement without `;`.
2. **Fails closed on the body — the complete statement sequence is pinned.** `REVIEWED_SEQUENCE` in `sql_guard.py` lists all 15 statements in order with the SHA-256 of each statement's comment-free, whitespace-collapsed text (the `DO` block is pinned by its normalised body instead). A changed, added, removed or reordered statement fails closed until a human reviews it and updates the table in the same change. That covers every part of `CREATE TABLE ops.operational_events` (a new column, default, expression, sequence/identity/generated clause, collation, or constraint change) as well as grants, policy, index and role settings. Behind the pin, independent checks still run: transaction control (`BEGIN/START/COMMIT/END/ROLLBACK/ABORT/SAVEPOINT/RELEASE/PREPARE`, `… AND CHAIN`, `… PREPARED`), `SET ROLE/RESET ROLE/SET SESSION AUTHORIZATION`, `CONCURRENTLY`, the reviewed-pattern/target match, a forbidden-clause scan of the table definition (references, inheritance, partition, sequences, identity, generated, collate, temp/unlogged, `AS SELECT`, `LIKE`), and a default audit (only `gen_random_uuid()`, `now()`, `'info'`, `'{}'::jsonb`), so a careless re-pin of a bad table still trips them. Backslashes are rejected inside every literal, quoted identifier and dollar body (their meaning depends on `standard_conforming_strings`; the pre-check also refuses to run unless that setting is `on`). The `DO` comparison strips comments *quote-aware* (a `--` inside `'…'` or `"…"` is data). Words such as `COMMIT` inside comments, strings or non-`DO` dollar quotes are not flagged.
3. **Pre-check on an independent read-only connection A.** Refuses to start (exit 2, nothing run) if `standard_conforming_strings` is not `on`, or if schema `ops`, the table, role `ops_writer`, the probe role or migration `002` already exists, if PostgreSQL < 16, or if the `procurement` schema does not have exactly 10 tables. Takes the baseline (`schema_migrations` count, row count of each procurement table).
4. **One harness-owned transaction on connection B** (`autocommit=True`, explicit `BEGIN`; the harness source never issues `COMMIT`). After *every* statement it reads the server's transaction status. `idle` mid-run means the transaction ended without the harness asking: it **stops immediately**, issues no rollback, reports `POSSIBLE PERSISTENT CHANGES` (exit 4) and requires manual review; it never claims a later `ROLLBACK` could undo a commit. A test injects a `COMMIT` past the guard to prove this path.
5. **Identity.** `GRANT … WITH SET TRUE` of `ops_writer` and of a temporary probe role to the connecting role (inside the transaction; PostgreSQL 16+ semantics, **to verify**). Each `SET ROLE` happens inside a savepoint, is followed by a `current_user`/`session_user` assertion, and is undone by `ROLLBACK TO` plus an explicit `RESET ROLE` and a second assertion; a mismatch aborts.
6. **Cases.** Each case is one statement inside `SAVEPOINT s` … `ROLLBACK TO s` / `RELEASE s` (valid rows are undone too, so keys never collide). Run as `ops_writer`: the 17 valid rows; the 52 invalid rows, each of which must fail with the exact SQLSTATE **and** one of the constraints that row violates (`DB_EXPECT`, so "rejected for the wrong reason" fails); plain duplicate → `23505` on the unique constraint; `ON CONFLICT DO NOTHING` → rowcount 1 then 0; `INSERT … RETURNING` → `42501`; `SELECT/UPDATE/DELETE/TRUNCATE/ALTER/DROP/CREATE POLICY/ALTER OWNER` on the events table and `SELECT/INSERT/ALTER/DROP/TRUNCATE` on a **uniquely named scratch table created inside the transaction** (owner-owned, nothing granted; so a denial can only be a privilege denial, never "does not exist") → `42501`; `CREATE TABLE` in `ops`, `public`, `procurement`, `CREATE SCHEMA`, `CREATE ROLE` → `42501`; **public-schema audit:** the migration identity creates a real scratch table `public.rehearsal_public_<tag>` inside the transaction (if it cannot, the run records the limitation and **fails closed**, it does not skip the checks); the harness confirms the table exists, that `ops_writer` has no effective privilege on it (default ACLs included) and no `CREATE` on `public`, then runs the **relation audit from the catalogs** (`pg_class` joined to `pg_namespace`, not `pg_tables`): every existing `public` relation of kind table, partitioned table, view, materialized view, foreign table and sequence is listed, and for each the *effective* privileges of `ops_writer` (including those reaching it through `PUBLIC` or role membership, because `has_*_privilege` evaluates them) are read: `SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` plus any column-level `SELECT/INSERT/UPDATE/REFERENCES` for the table-like kinds, and `USAGE, SELECT, UPDATE` for sequences. Any privilege is a FAIL, reported with the relation name and kind. A second, set-based catalog query repeats the test over **all non-system schemas** (everything except `pg_*` and `information_schema`) and fails if `ops_writer` holds any privilege on any relation other than `ops.operational_events`; a third fails if it has `CREATE` on any schema. These are catalog reads only: no sequence function (`nextval/currval/setval`) is ever called, identifiers are quoted with `qi()` (embedded quotes doubled), and **no SQL is ever executed against an existing `public` relation**: a view, materialized view, foreign table or table with triggers, policies or functions could run code with side effects, so existing relations are proven from the catalogs only (their names appear solely as arguments of the `has_*_privilege` functions). Live denial tests run only on objects the harness creates itself. Then, as `ops_writer`, `SELECT/INSERT/UPDATE/DELETE/TRUNCATE/ALTER/DROP` on the scratch table, each of which must fail with `42501` (a `42P01` "missing" is a FAIL, so a denial can only be a privilege denial). No privilege is granted to make a check pass. Objects that PostgreSQL or Supabase grant to `PUBLIC` by design (for example some extension views) will surface as findings for a human to judge; nothing is silently allow-listed. Catalog metadata readable by everyone (`pg_catalog`, `information_schema`) is out of scope. **`procurement` is audited the same way, catalog-only:** the harness asserts there are exactly 10 `procurement` tables, lists every `procurement` relation of every kind from `pg_class`, and records one check per relation (`ops_writer holds no privilege on procurement.<name> (<kind>)`) from `has_table_privilege` / `has_any_column_privilege` / `has_sequence_privilege`; **no `SELECT` or `INSERT` is executed against any existing `procurement` relation** (the earlier per-table `SELECT … LIMIT 1` and the `INSERT` into `schema_migrations` were removed). The only `procurement` statement involving the role is the denial test `CREATE TABLE procurement.rehearsal_new_<tag>` of a name that does not exist. Catalog audit: role flags, no memberships, table privileges = `INSERT` only, schema `ops` `USAGE` yes/`CREATE` no, no `procurement` privilege, API roles (`anon`, `authenticated`, `service_role`) have nothing on `ops`.
7. **RLS proof.** A probe role (`NOLOGIN NOBYPASSRLS`, no policy) is explicitly granted schema `USAGE` and table `SELECT, INSERT`; the harness *verifies* those grants and `rolbypassrls = false` first. Then: the owner seeds a row (inside a savepoint), the probe's `SELECT count(*)` must return 0 and the probe's `INSERT` must fail `42501`. Only then is "row level security denies" a conclusion about RLS and not about missing privileges.
8. **End and interruption.** Normal end, any exception, **and `KeyboardInterrupt`/`SystemExit`** all go through the same cleanup: if the transaction is still open (including `in error`, or an interrupt during `BEGIN` itself) the harness issues an explicit `ROLLBACK`, checks that the status is idle, closes B, and then **still runs the independent verification on a new connection** and prints the report; the interrupt does not escape. The report records `rehearsal interrupted`, and the result is never "ALL PASSED". If the connection is unusable (status unknown) or the `ROLLBACK` fails, the harness does **not** claim a rollback: it prints `ROLLBACK NOT CONFIRMED` and the result stays a failure until the verification shows no leftovers (the server also discards an open transaction when its session ends, but only the verification can show it). If the transaction is found already idle after a statement, or at cleanup, it is reported as possible persistent changes (exit 4). A second interrupt during cleanup or verification is caught and reported as "verification could not run" (exit 3). An interrupt during the read-only pre-check starts nothing (exit 2).
9. **Independent verification on a new connection C** (not B, read-only): schema `ops`, table, `ops_writer`, probe role absent; `002` not in `schema_migrations`; `schema_migrations` count and every procurement row count equal the baseline. Failure ⇒ `ROLLBACK VERIFICATION FAILED` (exit 3). If C cannot connect the result is also "not clean", never "clean".
Exit codes: 0 all checks passed, rollback confirmed by the harness and verified clean · 1 some check failed, the run was aborted/interrupted, or the rollback was not confirmed by the harness (verification found no leftovers) · 2 refused to start / guard refusal / cannot connect · 3 verification failed · 4 possible persistent changes. Output contains check names, SQLSTATE and constraint names only: no URLs, hosts, driver messages or parameter values.

### 8.5 Supabase connection and permission risks
Facts checked read-only on 11 Nov (no write): PostgreSQL **17.11**; connecting role `postgres` (not superuser; CREATEROLE, CREATEDB and BYPASSRLS true); `anon`, `authenticated`, `service_role`, `authenticator` exist; `ops_writer` and schema `ops` do not; `gen_random_uuid()` and `starts_with()` exist; **no default ACL applies to a new schema** (only `public`, `storage`, `graphql*`, `realtime` grant to the API roles), so a table created in `ops` starts owner-only (the explicit revokes are belt and braces); `procurement` objects are owner-only; applied migrations: `001`; `authenticator` role settings do not list the exposed API schemas, so the setting lives outside the database. Risks:
1. **Pooler login name.** The project uses the Supabase session pooler; custom roles are addressed as `role.project_ref`. Not yet tested for a role that does not exist — verify in P1; new roles should authenticate immediately (to verify).
2. **Password handling.** Set with `ALTER ROLE … PASSWORD` in the SQL editor, whose history stores the statement: use a long random value, never paste it in chat or Git, rotate if it appears anywhere. The draft contains no password (tested).
3. **Role settings through the pooler** (`search_path`, timeouts) may not apply; all statements are schema-qualified, so nothing depends on `search_path`.
4. **`ON CONFLICT`/`RETURNING` privileges** differ by form; P4/P5 prove the form used. Transaction-mode pooling breaks prepared statements: use the session pooler or disable prepares.
5. **`SET ROLE` rehearsal** needs a temporary membership grant (`GRANT … WITH SET TRUE`, PostgreSQL 16+ semantics); the harness issues it inside its transaction and refuses to run on older servers. If it is refused on Supabase the run aborts (and rolls back) rather than falling back to a weaker test.
6. **Free-tier behaviour:** a paused or unreachable project, connection limits and the 8-second API-role timeouts: event writes can fail for hours — hence the fallback below.
7. **Residual exposure:** `ops_writer` can read catalog metadata (table and column names) and the default `USAGE` on `public`; no row data.
8. **PostgREST exposure** of `ops` must stay off (P10); RLS with no SELECT policy is a second barrier for API roles, and `service_role`/`postgres` bypass RLS by design, hence the revokes.
9. **Time and disk:** migration `002` is DDL in the shared project; rollback is a reviewed script, not automatic.

### 8.6 Fallback if operational logging is unavailable (S2 implementation, after approval)
`PostgresEventSink`: `emit()` is **non-blocking** (bounded queue of 1,000, one daemon writer thread; connect timeout 3 s); each event is written with a parameterised `INSERT … ON CONFLICT DO NOTHING` (no conflict target, no `RETURNING`) using `to_row()`; **on any failure, or a full queue, the event is appended to `runs/events-outbox.jsonl`** (one JSON object per line, flushed), logging only the exception class/SQLSTATE. If `OPS_DATABASE_URL` is unset the sink runs **outbox-only** (events are kept, nothing is silently lost). An assessment is never delayed, failed or re-run by logging. A later `python -m src.api.flush_outbox` (dry-run by default, `--apply` to write) replays the file; it is idempotent through `event_key`. `/health` will add an `events` field (`ok`/`degraded`/`outbox-only`) — an S2 contract change (the current test pins four keys). If the outbox itself cannot be written the error is logged and the event is dropped (documented residual risk).

## 9. Notion `Assessment Reports` (PLANNED)
Created manually by the user; n8n creates/updates pages only. Properties: `Name`, `Request ID` (dedupe key), `Ingredient`, `Horizon (months)`, `Assessment date`, `Mode`, `Assessment status` (completed/partial only), `Archive status`, `Delivery status`, `Human review`, `Warnings`, `Claims removed`, `Report SHA-256`, `Total blocks`, `Schema version`, `Reviewer notes`.

**MVP acceptance criterion: the FULL report is archived in Notion, formatting may be simplified (tables as code blocks, flat blocks only). Never truncated.** If the whole report cannot be stored, `Archive status = incomplete`, the e-mail says so and attaches `report.md`; the demo is not "done" without one completely archived report.

**Rendering:** a planned FastAPI endpoint `GET /assessments/{id}/notion-blocks` returns `{report_sha256, total_blocks, blocks[]}` from the stored record, rendered by a deterministic, offline-tested function: flat top-level blocks only (no nested children), each rich-text ≤ 2,000 characters, appended in batches of ≤ 100. Limits and rate behaviour are **assumptions to verify against Notion's documentation in S3/S4.** demo-002 (23 KB, 153 lines, 21 headings, 22 table rows) is the sizing reference.

**Recovery from an interrupted upload without duplicate pages or duplicated content:**
1. Query by `Request ID` first. Found → reuse that page; several found (race) → use the oldest and record `duplicate_pages` in the event. Not found → create the page **with properties and no body**, `Archive status = incomplete`, `Report SHA-256` and `Total blocks` set from the endpoint.
2. Ground truth is the page itself: n8n counts the page's existing top-level children (`existing`) and appends only `blocks[existing:]` in batches. A crash between an append and any property update therefore cannot duplicate content, because the count is read from Notion, not from a counter.
3. Before resuming, the page's `Report SHA-256` must equal the endpoint's; a mismatch is a hard error (`archive.failed`), never a silent mix.
4. Completion: children count = `Total blocks` **and** SHA matches → `Archive status = stored` + `archive.stored`. Otherwise it stays `incomplete` and `archive.failed` is emitted after bounded retries (3, backoff, honouring `Retry-After`).
5. Re-running the workflow with the same `request_id` repeats steps 1–4 and is idempotent. No step ever calls `POST /assessments`.

`Validate` (action, request id, status, mode, hash format, ingredient `sunflower_oil`, horizon, date, `blocks` non-empty with `total_blocks == len(blocks)`, config ids) -> `Lookup page` by `Request ID` (sorted by creation time, **oldest wins**; a page is never created twice and a page with another hash is never touched) -> `Create page` **without body** (`Archive status = incomplete`, `Email status = not_requested`) unless it exists -> loop `List children` (cursor pagination) -> `Compare` (**every existing block, type and text, must equal the sent block at the same position**; extra or different content stops the workflow untouched with `ARCHIVE_CONTENT_MISMATCH`) -> `Append blocks` (<= 100 per request) -> list again. **`Mark stored` runs only after a listing shows all blocks with matching text**, and the answer's `report_sha256_echo` and `Archive status` are read back from Notion's reply. **Any Notion failure ends the execution with an answer** (`incomplete` once the page exists, `failed` 502 before it); the caller simply calls again and the same logic resumes from what is on the page (no waits, no inner retries after a write). Answer: `ok`, `request_id`, `archive_status` (`stored`, `duplicate_existing`, `incomplete`, `failed`), `notion_page_url`, `blocks_expected`, `blocks_found`, `report_sha256_echo`.
### 22.2 E-mail workflow (`POST /webhook/procurement-email`, separate Header Auth webhook)
`Validate email` (no recipient field accepted; PDF filename, type, size <= 5 MB, strict base64, `%PDF-`, `%%EOF`, hash format; config incl. the recipient) -> `PDF to binary` -> `Hash PDF` (**Crypto SHA-256 of the decoded binary**) -> `Hash matches?` (**compared with `attachment.sha256` before any lookup or send**) -> `Lookup page` -> `Ledger decision`: the page must be `stored` with the same `Report SHA-256`; `Email status` `sent` -> `already_sent`; `sending`/`unknown` -> `unknown` (no send; an operator resets the status in Notion); `not_requested`/`failed`/empty -> `Claim send` (`Email status = sending`, `Delivery ID = del-<request_id>`) -> `Restore PDF` (the verified binary; throws if missing) -> `Gmail send` (real send, not a draft; fixed recipient from `Config`; text = Executive Summary + **the page URL returned by Notion** + the PDF; retry off) -> `Record sent` (`sent` + `Email message id`). On a Gmail error the single `Record failed or unknown` node sets `failed` for an HTTP 4xx (not accepted, a resend is allowed) or `unknown` for anything else (never resent); the answer reports what Notion confirms. Answer: `ok`, `request_id`, `email_status` (`sent`, `already_sent`, `failed`, `unknown`), `message_id`, `delivery_id`, `attachment_sha256_echo` (hash computed on the attached binary), optional `ledger_warning`.
### 22.3 Operational error log (mandatory, best effort)
Both workflows end `Finalize outcome -> Respond -> Has error? -> Build error record -> Log error`. **The caller gets the answer first; the error record is written afterwards**, so logging can never change or delay the outcome; `Log error` has no retry and `continueRegularOutput`, so if the errors database is down the failure stays in the n8n execution history. Records carry only: Timestamp, Request ID (empty when invalid), Workflow, Component, Error code, Severity, `Status = open`, Execution ID, Retry count, Occurred during, stable Error ID `E-<workflow>-<request_id|noid>-<code>`; never exception text, secrets, report text or PDF content.

### 24.7 Draft-repair selection (13 Nov 2026) - IMPLEMENTED, TESTED OFFLINE, NOT RE-RUN LIVE
Finding from the seven repaired live runs of 13 Nov: the repair step (`DRAFT_REPAIR`) only receives the list of problems and the model regenerates the whole draft. In four runs the repaired draft lost more items to validation than the original draft had flagged (for example run `ui-20261113-015628-ccc371`: 3 flagged items in the original, 5 removed after the repair, among them two supplier leads that the first validation had not flagged). Nothing was changed in the research, the validators or their thresholds.

Change (`src/agent/validation.py`, `src/agent/graph.py`): the original draft is kept while the repair runs; when the repair budget is used up both drafts go through the same `prune_unsupported` process, `_enforce_no_dangling` guarantees that no mitigation or action refers to a removed risk, and `select_candidate` picks one: (1) only a draft with no unfixable problem is eligible; (2) most complete risk -> mitigation -> action chains; (3) most retained verified items; (4) a genuine tie goes to the repaired draft. Diagnostics: the validate step of the trace now carries `selection` (both candidates' chains, retained and removed counts, and the choice) and `discarded` (per discarded claim: kind, id, reason, cited source ids, and quote and source excerpts of at most 200 characters; public web text only).
